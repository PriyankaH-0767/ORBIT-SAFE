## 1. Overview & Scope

The D-DATO frontend is a modern React 19 + TypeScript + Vite web application styled with Tailwind CSS. It serves as the primary presentation and user interaction layer for mission planning, execution tracking, screening results analysis, risk density exploration, 3D orbital trajectory visualization, external reference validation, and data artifact exports.

### 1.1 Complete Feature Set (P19–P24):
1. **Mission Planning Interface (P19)**: 6-section accessible configuration form with real-time candidate grid estimation (capped at 300 candidates) and comprehensive orbital parameter defaults.
2. **Asynchronous Execution Progress (P19)**: Real-time run polling, dynamic stage progression (ingestion → candidate generation → fuel estimation → conjunction screening → risk scoring → ranking), and error handling with retry triggers.
3. **Screening Results Dashboard (P20)**: Authoritative headline summary metrics, paginated candidate rankings with telemetry detail drawers, and close-approach conjunction event tables.
4. **Interactive 2D Risk Heatmap (P21)**: Continuous Viridis color scale Plotly heatmap visualizing screening risk scores across deployment delays and altitudes, with inclination slice filtering.
5. **Interactive 3D Orbital Globe (P22)**: CesiumJS 3D viewer rendering candidate tracks, debris trajectories, and conjunction encounters with explicit TEME-to-pseudo-fixed coordinate frame transformation.
6. **External Reference Validation Dashboard (P23)**: Benchmark comparison against external reference datasets (SOCRATES) with explicit data provenance badges, count cards, descriptive comparison metrics, and matched event cross-linking.
7. **Artifact Exports & Reporting (P24)**: Direct browser downloads of machine-readable multi-CSV ZIP packages and executive PDF screening reports generated by the backend.

### Non-Operational Notice
> [!IMPORTANT]
> D-DATO is an early-stage screening and planning aid. It does **not** provide operational collision assessment, true collision probability ($P_c$), maneuver approval, or launch COLA clearance.

### Core Architectural Principles:
1. **Frontend Never Derives Orbital Mechanics**: All Keplerian conversions, SGP4 propagations, J2 drift calculations, golden-section TCA refinements, delta-v budgets, and risk scores are computed exclusively by the backend.
2. **Frontend Consumes Persisted Contracts**: Results are fetched directly from frozen backend endpoints (`/api/v1/runs/{run_id}`, `/api/v1/runs/{run_id}/candidates`, `/api/v1/runs/{run_id}/events`, `/api/v1/runs/{run_id}/heatmap`, `/api/v1/runs/{run_id}/globe`).
3. **Coordinate System Honesty**: The backend globe API outputs positions in **TEME (km)** (True Equator, Mean Equinox). Cesium's globe is rendered in an Earth-fixed rotating frame. The frontend explicitly transforms TEME coordinates to Cesium's pseudo-fixed frame using `Cesium.Transforms.computeTemeToPseudoFixedMatrix(julianDate)` and discloses this in the user interface.
4. **Offline & Self-Contained**: The 3D globe does not require a Cesium Ion token or external cloud accounts. It utilizes Cesium's local `NaturalEarthII` offline tilemap imagery and ellipsoid terrain.
5. **Authoritative Run Status**: Headline summary metrics (Candidates Evaluated, Candidates Ranked, Conjunction Events) are read strictly from `GET /api/v1/runs/{run_id}` and are never aggregated or recalculated from paginated arrays on the client.
6. **Strict Separation of Concerns**: Frontend displays backend-computed rankings, metrics, and event markers without recomputing, re-ranking, or altering numerical outputs.

## 6. Interactive 3D Orbit Globe (Phase P22)

### 6.1 Backend API Endpoint
- **Endpoint**: `GET /api/v1/runs/{run_id}/globe`
- **Query Parameters**:
  - `candidate_ids`: Optional comma-separated candidate IDs to isolate.
  - `sample_step_seconds`: Sampling cadence in seconds (default: 300s).
  - `max_candidates`: Maximum candidate tracks returned (default: 5, max: 20).
  - `max_debris`: Maximum debris tracks returned (default: 10, max: 50).
- **Payload Semantics**:
  - `time_bounds`: `start_time` and `end_time` (ISO 8601 UTC) defining the simulation interval.
  - `candidate_tracks`: List of candidate orbits with time-stamped TEME positions `[x_km, y_km, z_km]`.
  - `debris_tracks`: List of debris trajectories with time-stamped TEME positions `[x_km, y_km, z_km]`.
  - `event_markers`: Conjunction event points (`event_id`, `tca`, `miss_distance_km`, `primary_position_km`, `debris_position_km`).

### 6.2 Coordinate Frame Transformation (`cesiumFrames.ts`)
Cesium renders 3D entities in Earth-fixed (ITRF/ECEF) Cartesian coordinates. The backend outputs orbital tracks in **TEME (km)**.
The frontend converts each state point via:
```typescript
const metersTeme = new Cesium.Cartesian3(x_km * 1000, y_km * 1000, z_km * 1000);
const temeToFixed = Cesium.Transforms.computeTemeToPseudoFixedMatrix(julianDate);
const fixedPos = Cesium.Matrix3.multiplyByVector(temeToFixed, metersTeme, new Cesium.Cartesian3());
```
This guarantees physical correctness for visualization while remaining completely transparent about coordinate reference systems.

### 6.3 3D Viewer & Entity Architecture (`OrbitGlobe.tsx`)
- **Base Imagery**: Offline `TileMapServiceImageryProvider` loading `Assets/Textures/NaturalEarthII`.
- **Candidate Tracks**: Rendered as distinct cyan polylines with billboard position indicators. The currently selected candidate is visually highlighted in emerald with a thicker track.
- **Debris Tracks**: Rendered as amber polylines with point markers, toggled on/off via the control bar.
- **Conjunction Markers**: Conjunction sites at TCA rendered with prominent magenta/yellow point markers and billboard labels displaying miss distance.
- **Time Synchronization**: Cesium Clock is clamped to the simulation's `start_time` and `end_time`. Clock ticks synchronize the live UTC readout and interpolate satellite/debris positions along their backend-provided ephemerides.
- **Entity Interaction**: Clicking any candidate or event on the 3D globe immediately syncs with the corresponding detail drawer on the dashboard.

### 6.4 Controls & Legend (`GlobeControls.tsx`, `GlobeLegend.tsx`)
- **Animation Controls**: Play, Pause, Speed Multiplier (`1x`, `10x`, `60x`, `300x`).
- **Telemetry Readout**: Live UTC simulation clock.
- **Filter Controls**: Show/hide debris toggle, debris count limit selector (`5`, `10`, `25`, `50`), and sampling step interval (`60s`, `120s`, `300s`, `600s`).
- **Camera Tools**: "Focus Selected" (flies camera to active candidate) and "Reset View" (returns to global home perspective).
- **Coordinate Disclosure**: Clear legend stating `"Coordinate data: TEME | Display transform: TEME → Cesium pseudo-fixed frame"`.

## 8. External Reference Validation & Provenance Dashboard (Phase P23)

### 8.1 Backend API Endpoints (Frozen P16)
- **POST** `/api/v1/runs/{run_id}/validation`: Triggers external validation against a reference dataset.
- **GET** `/api/v1/runs/{run_id}/validation`: Retrieves latest persisted validation comparison for the run.
- **GET** `/api/v1/validations/{validation_id}`: Retrieves specific validation run record.

### 8.2 Explicit User-Triggered Workflow
Validation is strictly user-initiated. When `ResultsPage` mounts, it queries `GET /api/v1/runs/{run_id}/validation`. If a `404 VALIDATION_NOT_FOUND` is returned, it renders a clean empty state with configuration controls. Validation is never automatically executed on page load.
Once executed:
1. Controls are locked with an active spinner (`"Validating screening results…"`) to prevent duplicate simultaneous submissions.
2. The resulting `validation_id` is persisted and retrieved via `GET /runs/{run_id}/validation`.
3. Subsequent page loads or browser refreshes immediately load and display the persisted validation results.

### 8.3 Provenance & Data Origin Visibility
Validation data source and freshness are prominently displayed via dedicated badges:
- `socrates_demo_fixture`: Displayed as **Synthetic demo reference data** (amber badge).
- `socrates_cache`: Displayed as **Cached external reference data** (blue badge).
- `socrates_live`: Displayed as **Live external reference data** (emerald badge).
- Source snapshot epoch and comparison evaluation UTC timestamps are clearly itemized.

### 8.4 Strictly Non-Operational Terminology & Semantics
In compliance with project boundaries, the UI never presents validation results as "ground truth", "accuracy scores", "certified safety", or "collision probability":
- **Allowed Terminology**: `External Reference Validation`, `Reference Comparison`, `Matched Events`, `D-DATO-only Events`, `External-only Events`, `Reference Coverage`.
- **Summary Metrics**: 5 count cards (D-DATO Events, External Reference, Matched Events, D-DATO-only, External-only) plus descriptive comparison metrics (External Coverage %, D-DATO Match Rate %, Mean/Max |TCA Error|, Mean/Max |Miss Difference|). All missing/null metrics render strictly as `N/A` (never converted to 0).
- **Audit & Benchmark Comparison Tables**:
  * **Matched Events Table**: Paired events within tolerances with criteria tags and clickable Candidate cross-linking.
  * **D-DATO-only Table**: Neutral presentation of events absent in reference data.
  * **External-only Table**: Neutral presentation of reference events without pairing in candidate envelope.
  * **Backend Notes**: Direct rendering of the backend's explicit non-operational disclaimer and metadata notes.

## 9. Artifact Exports & Reporting (Phase P24)

### 9.1 Backend Export Endpoints
- **CSV Package**: `GET /api/v1/runs/{run_id}/exports/csv` (returns `application/zip`)
- **Executive PDF Report**: `GET /api/v1/runs/{run_id}/exports/pdf` (returns `application/pdf`)

### 9.2 Client-Side Download Lifecycle (`download.ts`, `exports.ts`)
- The frontend directly downloads backend-generated binary artifacts without client-side parsing or generation.
- **Filename Extraction**: Reads the HTTP `Content-Disposition` header (`filename="..."` or RFC 5987 `filename*=UTF-8''...`). If absent, cleanly falls back to `d-dato-{runId}-export.zip` or `d-dato-{runId}-report.pdf`.
- **Blob Lifecycle**: Uses temporary Object URLs (`window.URL.createObjectURL(blob)`), triggers a headless anchor click, and immediately schedules cleanup via `window.URL.revokeObjectURL`.
- **Concurrency & Duplication Protection**: Download buttons are disabled with active preparation spinners (`Preparing CSV…`, `Preparing PDF…`) while downloads are in flight to prevent duplicate requests.
- **Strict Non-Operational Labeling**: Cards describe machine-readable ZIP data and printable screening summaries without using misleading claims such as "certified safety", "official report", or "flight approval".
